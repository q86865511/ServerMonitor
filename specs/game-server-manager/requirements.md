## 概述

為個人(未來可擴及朋友)提供一套可擴充的遊戲專用伺服器管理與監控桌面工具。透過「遊戲範本」抽象,使新增一款遊戲主要是加一份範本而非改核心;首版以 Docker 為執行後端,支援 Minecraft 與 Palworld 的一鍵建立、監控、指令、自動復原、備份與告警。

## 範圍(含明確不做)

**包含(首版):**
- Windows 桌面 GUI 客戶端。
- 管理核心,與節點代理以 API 契約分離(單機同機部署)。
- Docker 執行後端,封裝於抽象「執行後端(RuntimeBackend)」介面之後。
- 遊戲範本系統:內建 Minecraft、Palworld 兩份範本,含變體/模組定義。
- 一鍵建立/部署伺服器實例;啟動/停止/重啟生命週期。
- 資源與狀態監控 + 即時 log 串流。
- RCON / REST 指令主控台。
- 自動重啟 / 崩潰復原(健康檢查、重試上限)。
- 排程備份 + 一鍵還原;保留策略。
- 告警通知(首版 Discord webhook;Email/SMTP 列次期)。
- 模組 / 模組包支援(Paper/Forge/Fabric 變體 + 模組包安裝,含工具內串接 CurseForge/Modrinth 搜尋下載)。

**明確不做(首版,防蔓延):**
- 多節點的實際遠端部署與其完整安全通訊層(只設計 API 契約,不實作跨機認證/加密)。
- 原生 SteamCMD 後端的完整實作(只留抽象介面 + mock 驗證)。
- 雲端 VM 隨需開機。
- Web 版 / 行動版介面。
- 多使用者帳號與權限系統(首版為單一本機操作者)。
- Windows-only 容器 / 反作弊相容處理。

## 需求

### R1 遊戲範本抽象與擴充
常態:系統應以「遊戲範本」定義每款遊戲的安裝來源、啟動參數、埠、設定檔位置與指令協定(RCON/REST),使新增遊戲僅需新增一份範本而不修改核心程式。

驗收條件:
- 定義一份明確的範本 schema;載入內建 Minecraft 與 Palworld 兩份範本後,GUI 能列出可建立的遊戲類型。
- 放入一份格式正確的新範本檔(不改核心程式)後,該遊戲類型出現在可建立清單。
- 範本檔缺必填欄位時,系統應拒絕載入該範本並於事件記錄標明缺哪個欄位,其餘範本不受影響。

### R2 一鍵建立伺服器實例
事件驅動:當使用者選定範本、填妥必要參數並確認建立時,系統應準備對應 Docker 映像並建立一個可啟動的伺服器實例。

驗收條件:
- 以 Minecraft 範本完成建立後,實例出現在清單且狀態為「已建立/未啟動」。
- 必填參數(如埠、記憶體上限)缺漏時,於建立前阻擋並明確提示缺哪一項。
- 新實例的對外埠與現有實例衝突時,系統應在建立前偵測並提示,不產生無法啟動的實例。

### R3 伺服器生命週期管理
常態:系統應提供對單一伺服器實例的啟動、停止、重啟操作。

驗收條件:
- 對已建立實例按「啟動」,對應容器進入 running,GUI 狀態於數秒內反映為「執行中」。
- 停止時採優雅關閉(先送停止指令/給寬限期再停容器),降低存檔損毀風險。
- 對執行中實例重複按「啟動」不重複建立容器,而是無操作或提示已在執行。

### R4 執行後端抽象(RuntimeBackend)
常態:系統應透過抽象「執行後端」介面操作所有伺服器,首版提供 Docker 實作,介面預留日後加入原生 SteamCMD 後端。

驗收條件:
- 核心對伺服器的所有操作(建立/啟停/查狀態/取 log/執行指令)皆經 RuntimeBackend 介面,不散落直呼 Docker SDK。
- 介面至少涵蓋:建立、啟動、停止、狀態查詢、log 串流、執行指令(exec)。
- 以一個 mock 後端替換 Docker 實作,核心生命週期流程仍能於單元測試中跑通。

### R5 控制核心與節點代理分離
常態:系統應以定義好的 API 契約分離「管理核心」與「節點代理」;首版單機時兩者同機,但核心對代理的操作經該 API 而非行程內直接呼叫。

驗收條件:
- 存在一份節點代理 API 契約,涵蓋:實例 CRUD、啟停、狀態、log、指令、資源指標。
- 呼叫路徑「桌面客戶端 → 管理核心 → 節點代理」可追蹤;單機時代理以本機端點回應。
- 邊界:代理端點無回應時,核心應將該節點標記為離線並於 GUI 顯示,而非整體當掉。

### R6 資源與狀態監控 + 即時 log
持續狀態:於伺服器執行期間,系統應持續採集 CPU/記憶體/磁碟用量與線上狀態並於 GUI 即時顯示;使用者開啟某實例主控台時應串流其即時 log。

驗收條件:
- 執行中實例的 CPU% 與記憶體用量在 GUI 以固定間隔(≤5 秒)更新。
- 開啟主控台可看到容器 stdout 的即時新行(串流,無需手動刷新)。
- 玩家數:範本支援查詢者顯示於實例卡片;不支援者顯示「不適用」而非錯誤。

### R7 RCON / 指令主控台
事件驅動:當使用者在主控台輸入遊戲指令並送出時,系統應透過範本定義的協定(Minecraft RCON、Palworld REST/RCON)送達伺服器並回顯結果。

驗收條件:
- 對執行中 Minecraft 實例送出 RCON 指令(如 `list`)能回顯結果。
- 對執行中 Palworld 實例,REST API 與 RCON 兩種協定皆可送出指令並回顯(首版兩者都做)。
- 未設定/未啟用指令協定的實例,主控台輸入應停用並提示原因。
- 連線失敗時顯示明確錯誤訊息,GUI 不卡死。

### R8 自動重啟 / 崩潰復原
事件驅動:當受監控的伺服器非預期結束(崩潰)時,系統應依該實例設定自動嘗試重啟並記錄事件;常態:系統應支援對實例設定排程重啟。

驗收條件:
- 模擬崩潰(外部殺掉容器)後,若該實例啟用自動復原,系統於設定的重試間隔內重新啟動它。
- 連續崩潰達設定上限(如 5 分鐘內 3 次)時停止自動重試並發告警,避免無限重啟迴圈。
- 排程重啟於設定時間觸發;若範本支援遊戲內公告,重啟前先發出公告。

### R9 排程備份 + 還原
條件:若實例啟用排程備份,則系統應於設定時點打包其資料目錄至備份儲存區,並套用保留策略(如保留最近 N 份);事件驅動:當使用者選擇某備份還原時,系統應停止實例、還原資料後可重新啟動。

驗收條件:
- 排程觸發後產生一份可辨識(含時間戳、實例、遊戲)的備份檔於指定備份目錄。
- 保留策略為 N 時,備份數超過 N 自動刪除最舊者。
- 還原前若實例執行中,系統應先停止再還原以免寫入衝突;還原後資料內容與所選備份一致。

### R10 告警通知
事件驅動:當發生崩潰、連續重啟失敗、備份失敗、或資源超過使用者設定門檻時,系統應透過已設定管道發送告警。

驗收條件:
- 觸發一次崩潰事件後,設定的 Discord webhook 收到含實例名與事件類型的訊息。
- 未設定任何管道時,告警僅記錄於本機事件記錄且不報錯。
- 告警送出失敗時重試有限次數並記錄,不阻塞主流程(監控/生命週期照常)。

### R11 模組 / 模組包支援
常態:系統應允許以範本變體選擇伺服器類型(如 Minecraft 的 Vanilla/Paper/Forge/Fabric),並支援安裝模組/外掛與載入模組包。

驗收條件:
- 以 Paper 變體建立 Minecraft 實例可成功啟動,且放入外掛目錄的外掛啟動後生效。
- 於工具內搜尋 Modrinth/CurseForge 模組包,選定後自動下載並套用到新實例(CurseForge 若需 API 金鑰,於設定填入)。
- 手動壓縮檔匯入的模組包建立實例,啟動後模組生效。
- 不相容的變體/模組組合在建立前給出可理解的錯誤(能靜態檢查的部分),而非啟動後才崩潰。

### R12 設定與資料持久化
常態:系統應以 UTF-8 儲存所有設定與實例中繼資料;重啟工具後實例清單、範本、排程與告警設定皆保留。

驗收條件:
- 建立數個實例並設定排程後重啟工具,清單與設定完整重現。
- 設定檔毀損或缺欄位時,系統以預設值啟動並於事件記錄標明,不整體崩潰。

## 非功能需求

- **相容性**:主機為 Windows 11;Docker 經 WSL2 / Docker Desktop;桌面應用為 Windows 原生可執行檔。
- **效能**:工具本身(GUI + 核心)閒置資源占用應遠低於單一遊戲伺服器;監控輪詢不顯著增加受監控伺服器負載。
- **安全**:RCON 密碼、webhook URL、Email 憑證等敏感資訊應以本機安全方式儲存(加密或作業系統金鑰庫),不以明文寫入一般設定檔。
- **可靠**:管理核心崩潰不應導致遊戲伺服器容器一併停止(容器生命週期與工具解耦)。
- **生命週期**:依裁決,自動化(監控/自動復原/排程備份/告警)僅於 GUI 應用開啟時運作;關閉應用不停止已在執行的遊戲容器(由 Docker 維持)。
- **擴充**:新增遊戲以「加範本」為主;新增執行後端以「實作 RuntimeBackend 介面」為主。
