## 概述

為個人(未來可擴及朋友)提供一套可擴充的遊戲專用伺服器管理與監控桌面工具。透過「遊戲範本」抽象,使新增一款遊戲(且沿用既有 runtime/指令/健康檢查 adapter 者)主要是加一份範本而非改核心;首版以 Docker 為執行後端,支援 Minecraft 與 Palworld 的一鍵建立、監控、指令、自動復原、備份與告警。

## 範圍(含明確不做)

**包含(首版):**
- Windows 桌面 GUI 客戶端。
- 管理核心,與節點代理以「有版本、有認證」的 API 契約分離(單機同機部署,走 loopback)。
- Docker 執行後端,封裝於抽象「執行後端(RuntimeBackend)」介面之後;含備份/還原所需的 Archive/Restore 能力。
- 遊戲範本系統:內建 Minecraft、Palworld 兩份範本,含變體/模組定義與版本化 schema。
- 一鍵建立/部署伺服器實例;啟動/停止/重啟生命週期;啟動對帳與孤兒容器處理。
- 資源與狀態監控(CPU/RAM/資料磁碟用量/線上狀態)+ 即時 log 串流。
- 指令主控台:Minecraft RCON;Palworld REST 具名動作。
- 自動重啟 / 崩潰復原(狀態機、健康探針、重試上限、序列化操作)。
- 排程備份 + 一鍵還原;保留策略;一致性快照。
- 告警通知(首版 Discord webhook;含門檻窗口/去重/cooldown)。
- 結構化事件記錄(可查詢)。
- 模組 / 模組包支援(Paper/Forge/Fabric 變體 + 模組包安裝,首版以 itzg 映像原生機制為唯一安裝擁有者 + 手動受限檔案)。
- 設定與資料持久化;敏感值存 OS 金鑰庫;DB 毀損隔離復原。

**明確不做(首版,防蔓延):**
- 多節點的實際遠端部署與其完整安全通訊層(只設計「有版本」的 loopback API 契約,不實作 `cmd/agent`、跨機 TLS、節點註冊/部署)。
- 原生 SteamCMD 後端的完整實作(只留抽象介面 + mock 驗證)。
- **自建 Modrinth/CurseForge 下載器/相依解析器**(首版改用 itzg 映像原生 `MODRINTH`/`AUTO_CURSEFORGE` + 手動受限檔案;自建串接延後)。
- **Palworld RCON 首版列 legacy**(需官方現況查證後才啟用,不列入首版驗收);首版 Palworld 指令以官方 REST 具名動作為準。
- 雲端 VM 隨需開機。
- Web 版 / 行動版介面。
- 多使用者帳號與權限系統(首版為單一本機操作者)。
- Windows-only 容器 / 反作弊相容處理。

## 需求

### R1 遊戲範本抽象與擴充
常態:系統應以版本化的「遊戲範本」定義每款遊戲的安裝來源、變體、埠、參數、資料目錄、指令協定與健康檢查,使新增「沿用既有 runtime/指令/健康 adapter」的遊戲僅需新增一份範本而不修改核心程式。

驗收條件:
- 範本 schema 有明確版本欄位(如 `schema_version`);載入內建 Minecraft、Palworld 範本後,GUI 列出可建立的遊戲類型與其變體。
- 以第三款代表性測試範本(沿用既有 Docker runtime 與現有指令/健康 adapter)、**不改核心程式**,可完成「載入 → 建立 → 啟動 → 查詢狀態」全鏈路。
- 範本缺必填欄位、`schema_version` 不支援、或 template ID 重複時,系統拒絕載入該範本並寫入一筆含原因與缺漏欄位的結構化事件(見 R14),其餘範本不受影響。
- 需要新增 runtime/指令/健康 adapter 的遊戲,不屬「只加範本」範圍,範本載入時應明確標示所需 adapter 是否存在。

### R2 一鍵建立伺服器實例
事件驅動:當使用者選定範本、變體、填妥必要參數並確認建立時,系統應準備對應 Docker 映像並建立一個處於 `Created` 狀態的伺服器實例,且整個建立為原子操作。

驗收條件:
- 建立成功後,實例以穩定 UUID 登錄於 DB,狀態為 `Created`,並記錄其 runtime(容器)ID 與 Docker 標籤(含該 UUID)。
- 必填參數缺漏時於建立前阻擋,並明確指出缺哪一項;Minecraft 範本未接受 EULA 時不得建立(不暗中預設)。
- 埠衝突以 `(bind IP, protocol, port)` 為唯一鍵在建立前偵測並提示,不產生無法啟動的實例。
- 建立任一步驟(拉映像/建容器/寫 DB)失敗時,系統回滾:不遺留孤兒容器,也不遺留孤兒 DB 紀錄,並寫入失敗事件。

### R3 伺服器生命週期管理
常態:系統應提供對單一伺服器實例的啟動、停止、重啟操作,且同一實例的操作序列化(不併發)。

驗收條件:
- 對 `Created`/`Stopped` 實例按「啟動」,系統輪詢至容器 `Running`;於逾時上限(預設 60 秒,可設定)內未達 `Running` 則標記失敗並報明確錯誤。
- 停止採優雅關閉:先送該範本定義的停止指令(若有)、給寬限期(預設 30 秒,可設定),逾時才強制停止容器;狀態轉為 `Stopped`。
- 重啟後系統斷言仍是同一 runtime ID 的容器回到 `Running`(重啟=Stop+Start 編排,非新建容器)。
- 對 `Running` 實例重複按「啟動」為冪等:不重建容器,回報「已在執行」。
- 「停止」屬計畫性操作,應標記 planned-stop 意圖,使 R8 的崩潰偵測不將其誤判為崩潰。

### R4 執行後端抽象(RuntimeBackend)
常態:系統應透過抽象「執行後端」介面操作所有伺服器容器生命週期與資料封存,首版提供 Docker 實作,介面預留日後加入原生 SteamCMD 後端。

驗收條件:
- 核心對容器的所有操作(建立/啟停/查狀態/列舉/移除/取 log/程序 exec/資源指標/封存/還原)皆經 RuntimeBackend 介面,不散落直呼 Docker SDK。
- 介面至少涵蓋:Create、Start、Stop、Status、List、Inspect、Remove、Logs(串流)、ExecProcess(容器內程序執行)、Stats、Archive、Restore。
- 遊戲內指令(RCON/REST)**不經** `ExecProcess`,而經獨立的 `GameCommandAdapter`(見 R7),兩者語意分離。
- 以 mock 後端替換 Docker 實作,核心生命週期流程於單元/整合測試中跑通(含 core→agent→mock 路徑)。

### R5 控制核心與節點代理分離(有版本、有認證)
常態:系統應以「有版本、有認證」的 API 契約分離「管理核心」與「節點代理」;首版單機時兩者同機走 loopback,但核心對代理的操作經該 API 而非行程內直接呼叫。

驗收條件:
- 存在一份版本化的節點代理 API 契約(建議 OpenAPI 或等價),涵蓋:實例的 建立/列舉/查詢/移除、啟停/重啟、狀態、資源指標串流、事件串流、log 串流、遊戲指令、備份清單/建立/還原、health;各端點定義 request/response、錯誤碼與冪等鍵。
- 代理僅綁 loopback,且要求每次啟動生成的記憶體 bearer token;未帶正確 token 的 HTTP/WS 請求一律拒絕;WS 檢查 Origin。
- 呼叫路徑「桌面客戶端 → 管理核心 → 節點代理」可追蹤;代理端點無回應時,核心將該節點標記為離線並於 GUI 顯示,而非整體當掉。

### R6 資源與狀態監控 + 即時 log
持續狀態:於伺服器執行期間,系統應持續採集 CPU%、記憶體用量、**資料磁碟用量**與**線上狀態**並於 GUI 即時顯示;使用者開啟某實例主控台時應串流其即時 log。

驗收條件:
- 執行中實例的 CPU%(定義正規化基準)與記憶體用量在 GUI 以固定間隔(≤5 秒)更新。
- 資料磁碟用量以 `data_dirs` 對應的宿主路徑或 helper 採集,顯示已用量;無法採集時顯示「不適用」而非錯誤(明確與 Docker 累積 block I/O 區分)。
- 線上狀態依範本定義的探針(REST/RCON/TCP)判定;不支援者顯示「不適用」。
- 開啟主控台可看到容器 stdout 的即時新行(串流、無需手動刷新);log 推送有背壓保護(有界緩衝、批次、丟棄提示),高流量下 GUI 不卡死。
- 玩家數:範本支援查詢者顯示於實例卡片;不支援者顯示「不適用」。

### R7 指令主控台(Minecraft RCON;Palworld REST 具名動作)
事件驅動:當使用者於主控台送出指令時,系統應依範本定義的指令協定送達伺服器並回顯結果。

驗收條件:
- 範本以 `command_protocols[]` 表達可含多種協定;RCON 為 raw console(自由指令字串),REST 為具名結構化動作(各定義 method/path/body/response/憑證/埠)。
- 對執行中 Minecraft 實例送 RCON 指令(如 `list`)能回顯結果。
- 對執行中 Palworld 實例,以 REST 具名動作(如查詢玩家、公告)可執行並回顯;**Palworld RCON 首版列 legacy,不列入首版驗收**(需官方現況查證後才啟用)。
- 未設定/未啟用指令協定的實例,對應主控台輸入停用並提示原因;連線失敗顯示明確錯誤,GUI 不卡死。

### R8 自動重啟 / 崩潰復原(狀態機 + 健康探針)
事件驅動:當受監控實例「非計畫性」結束或健康探針判定卡死時,系統應依該實例設定自動嘗試重啟並記錄事件;常態:系統應支援對實例設定排程重啟。

驗收條件:
- 系統維護每實例的 desired/observed 狀態機;容器 `die` 事件需比對 planned-stop 意圖:計畫性停止/排程重啟/還原前停機**不**觸發自動重啟,僅真正非預期退出或健康探針失敗才觸發。
- 崩潰後於設定重試間隔內(含 startup grace)重啟;連續崩潰達上限(預設 5 分鐘 3 次,可設定)時停止自動重試並發告警,不進入無限重啟。
- 「容器 running 但遊戲卡死」由健康探針(REST/RCON/TCP,依範本)偵測並納入復原判定。
- 排程重啟於設定時間觸發(以 UTC 記錄,處理時區/DST);若範本支援遊戲內公告,重啟前先發公告;同一實例操作序列化,避免與備份/還原互撞。

### R9 排程備份 + 還原(一致性 + 原子還原)
條件:若實例啟用排程備份,則系統應於設定時點透過 RuntimeBackend 的 Archive 能力打包其資料至備份儲存區,並套用保留策略;事件驅動:當使用者選擇某備份還原時,系統應以驗證後的原子方式還原並恢復該實例原本的 desired 狀態。

驗收條件:
- 明定資料策略(bind mount 或 named volume)與封存方式;備份前取得一致快照(遊戲 save/flush hook 或先停機)。
- 排程觸發後產生一份可辨識(時間戳、實例 UUID、遊戲、含 checksum)的備份於指定目錄;GUI 可列出某實例的備份清單。
- 保留策略 N(預設值可設定)時,超過 N 自動刪除最舊者;刪除失敗記錄事件不中斷主流程。
- 還原:先停止實例 → staging 驗證(checksum)→ 原子切換 → 恢復實例**原本**的 desired 狀態(原為停止則保持停止,不無條件啟動);還原後資料與所選備份一致。

### R10 告警通知(門檻窗口 + 去重 + cooldown)
事件驅動:當發生崩潰、連續重啟失敗、備份失敗、或資源持續超過使用者設定門檻時,系統應透過已設定管道發送告警。

驗收條件:
- 四類事件(崩潰/重啟失敗/備份失敗/資源超標)各有固定觸發輸入與可斷言的 payload(含實例名、事件類型、時間)。
- 資源門檻採持續窗口 + 遲滯(hysteresis)+ cooldown:短暫尖峰不觸發,恢復後解除;同類告警在 cooldown(預設 5 分鐘)內去重,不每 5 秒轟炸。
- 未設定任何管道時,告警僅寫入事件記錄且不報錯。
- 送出失敗依明訂策略重試(次數、timeout、對 429 遵守 `Retry-After`、對 5xx 退避),失敗記錄且不阻塞主流程。

### R11 模組 / 模組包支援(itzg 原生為唯一安裝擁有者)
常態:系統應允許以範本變體選擇伺服器類型(Vanilla/Paper/Forge/Fabric),並經 itzg 映像原生機制安裝模組包;工具本身不與 itzg 爭奪同一資料目錄的安裝擁有權。

驗收條件:
- 範本列出 loader/遊戲版本支援矩陣;以 Paper 變體建立 Minecraft 實例可啟動,放入外掛目錄的外掛啟動後生效。
- 以 itzg 原生 `MODRINTH`/`AUTO_CURSEFORGE`(CurseForge 需 `CF_API_KEY`)指定模組包建立實例,啟動後模組生效;**工具不另行解壓到 `/data`**,由 itzg 為唯一安裝擁有者以免互刪。
- 手動受限檔案流程:定義可接受格式(mrpack / CurseForge manifest / zip),手動匯入後建立實例啟動生效。
- 不相容的變體/loader/版本組合在建立前依支援矩陣給出可理解錯誤(可否證的靜態檢查),而非啟動後才崩潰。

### R12 設定與資料持久化(毀損隔離復原 + 敏感值參照)
常態:系統應以 UTF-8 儲存設定與實例中繼資料;重啟工具後實例清單、範本、排程與告警設定皆保留。

驗收條件:
- 建立數個實例並設定排程後重啟工具,清單與設定完整重現;DB 具 schema 版本與遷移機制。
- SQLite 毀損時進入隔離(quarantine)+ 降級復原模式:不靜默以空庫覆寫原檔(避免既有容器變孤兒),並發事件提示;一般設定檔毀損則以預設值啟動並記錄。
- 敏感值(RCON/webhook)在 DB 以「金鑰庫參照」表示,實體存 OS 金鑰庫;明訂「工具中繼資料不存明文」;遊戲 runtime 本身若需把 RCON/AdminPassword 寫入其設定檔或容器環境,列為明確例外並註明其 ACL 與備份處理。

### R13 啟動對帳與單一實例
常態:系統啟動時應以 Docker 標籤/runtime ID 對帳 DB 與實際容器狀態,並確保同時只有一個應用程序實例在管理同一組容器。

驗收條件:
- 啟動時 List/Inspect 實際容器,與 DB 對帳:DB 有而容器不存在→標記;容器有 UUID 標籤而 DB 無→標為孤兒並提示;狀態不一致→以實際為準更新 observed 並記錄。
- GUI 關閉期間發生的容器狀態變化,於重開時經對帳反映(重建事件訂閱)。
- 偵測到另一應用程序實例已在執行時,後啟者拒絕接管並提示,避免雙寫。

### R14 結構化事件記錄
常態:系統應將關鍵事件(範本載入失敗、建立/啟停、崩潰、重啟、備份、還原、告警送出、對帳)寫入結構化、可查詢的事件記錄。

驗收條件:
- 每筆事件含 event code、時間(UTC)、severity、實例/節點關聯與訊息;非僅寫 stdout。
- GUI 或介面可依實例/類型/時間查詢事件;其他需求(R1/R8/R10/R12/R13)的「已記錄」驗收以 event code 與欄位判定。
- 事件記錄有保存/輪替策略(避免無限增長)。

## 非功能需求

- **相容性**:主機為 Windows 11;Docker 經 WSL2 / Docker Desktop;桌面應用為 Windows 原生可執行檔。指定最低 Docker Engine API 版本。
- **相依版本鎖定**:明訂 Go 版本、Wails 主版本(首版採 v2 stable)、Docker client 模組與版本、`modernc.org/sqlite` 與 `go-keyring` 版本(見 design.md)。
- **效能(可量測)**:於指定量測硬體與時間窗下,閒置時工具(GUI+核心)CPU 與 working set 有明確上限基準;每實例監控開銷與高流量 log 基準可量測且遠低於單一遊戲伺服器負載。
- **安全**:代理僅 loopback + 每次啟動 bearer token + WS Origin 檢查;RCON 密碼、webhook URL、Email 憑證等以 OS 金鑰庫儲存,不明文寫入一般設定檔。
- **可靠**:管理核心崩潰不應導致遊戲伺服器容器一併停止(容器生命週期與工具解耦)。
- **生命週期**:自動化(監控/自動復原/排程備份/告警)僅於 GUI 應用開啟時運作;關閉應用不停止已在執行的遊戲容器(由 Docker 維持),重開經 R13 對帳恢復。
- **擴充**:新增「沿用既有 adapter」的遊戲以加範本為主;新增執行後端以實作 RuntimeBackend 介面為主。
